【库外菜品的营养补充】—— 贴在 LLM 节点提示词里,紧接在「食物库目录」那段的后面

上面那份目录里挑不到 foodId 的菜(比如「土豆炖牛肉」「煎饼果子」),去联网搜索
它的营养成分,然后把结果按下面这个形状填进 dishes 里对应的那一项:

  "per100g": { "kcal": 168, "protein": 9.2, "carb": 8.5, "fat": 9.8, "sodium": 480, "sugar": 1.2 },
  "source": "中国食物成分表(第6版)"

六个键**一个都不能少,名字一个都不能改**,单位和 App 食物库完全一致:

  kcal 千卡 ｜ protein / carb / fat / sugar 克 ｜ sodium 毫克

口径必须折算成下面这四条 —— 它们和库里那 58 条是**同一把尺子**,
折算不过来就说明这个数不能用:

1. **每 100g,不是每份、每碗、每盘。** 搜到「一碗 232 kcal」这种,先用份量
   折算成每 100g 再填。界面上加总的是每 100g 的值乘用户确认的克数,
   把按份的值直接填进来,总数会静默地偏掉。

2. **熟食、可食部,不是生食材。** 「大米(生)346」和「米饭(熟)116」差 3 倍,
   两个都搜得到、都有出处,填错了在界面上看不出来。

3. **烹调油盐已经折算进这道菜。** 不要填「食材值 + 另加油盐」,库里那 58 条
   已经是折算过的。

4. **sugar 填的是「添加糖」,不含天然糖。** 水果的果糖、牛奶的乳糖都不算,
   所以苹果、香蕉那里是 0,可乐、蛋糕才是大值。搜到的多半是总糖,
   按这个定义折算 —— 不然「控糖」会变成「别吃水果」,那是错的建议。

source 写你实际用到的那份来源的名字(成分表版本、数据库名、或者具体页面)。

**搜不到合口径的值,就不要输出 per100g 和 source 这两个键。** 宁可让这道菜在
App 里显式地「按 0 计」并且用户看得见,也不要填一个口径不对的数字 ——
口径不对的错数字比明着缺一项更糟,因为它进了总数而没有任何人看得出来。
这一条和目录那条「不要为了填满字段而编一个 foodId」是同一条规矩。

目录里**有**对应项的菜,照旧只输出 foodId,**不要**输出 per100g ——
库里的值和它是同一把尺子,不用你再去搜一遍。
