# 食衡 MealBalance

**记录一餐 → 看到营养分析 → 存进日记 → 首页的健康分和趋势跟着变。刷新之后，数据还在。**

一个手机优先的饮食健康管理 App。设计稿来自 Figma，代码是从零写的 ——
不是设计稿的截图拼贴，也不是点着好看但数据写死的原型。

React 19 · Vite 8 · TypeScript 7 · Tailwind CSS 4

> 🔗 在线体验：(https://meal-balance-eta.vercel.app/)
> 打开即用，不需要注册，不需要配置任何东西。
> 首次打开会先走三步建档（称呼/体征 → 目标/偏好 → 特殊时期/慢性病），
> **每一步都摆着「先用演示档案看看」** —— 点一下就装好一份 14 天的演示数据直达首页，
> 面试/演示的时候不想填也能一秒进入。
> 手机上全屏原生手感；电脑上会显示一台设备外框，方便截图。

## 能演示什么

七屏按 Figma 逐项还原（`402×874pt`，iPhone 17 母版），但真机上是响应式铺满的。
下面这些是**真的能跑**的，也是这个作品想证明的东西：

**1. 数据是真的在流动**
首页的健康分、今日摄入、餐次摘要，日记页的趋势与警示，结果页的每一条营养条 ——
全部由 `src/store/derive.ts` 从餐次记录**现算**，没有一个是写死的常量。
随便记一餐，所有页面的数字会同时变化。

**2. 刷新不丢**
记录写在 `localStorage`，带 schema 版本号。
在「我的」页可以一键恢复演示数据，或者清空重来 —— 方便面试官反复试。

**3. 健康分是可解释的**
不是神秘数字。三项扣分：钠（最多 −35）、热量偏离（−25）、蛋白质不足（−10），
每一项都带一句说明为什么掉了分。钠权重最高，因为这 App 的核心主张就是控盐。

**4. 改目标，判定立刻跟着变**
档案页可以调每日目标。把钠从 2000mg 调到 1200mg，
同一批记录会立刻从「合格」翻成「超标」，首页健康分跟着掉。
标尺可调，数字才不是摆设。

**5. 拍餐盘是真的在拍**
点相机图标会真的唤起后置摄像头（手机上），选中的照片经缩放后送去多模态模型识别菜品，
出结果前会让你确认一下每道菜的份量，识别结果可以改、可以归档，照片会以缩略图留在日记里。
链路见[拍餐盘的真实链路](#拍餐盘的真实链路)和[确认分量那一步](#确认分量那一步)。
没有 Key 的时候这一条会退回本地组菜，并在页面上说明「以下菜品为演示数据」。

**6. 档案里的每一条都有后果**
慢性病和特殊时期**真的会改每日配额**（高血压 → 钠 1500mg，孕期 → 热量 +300kcal），
不是勾着好看。改完档案页会多出一行「这些数字为什么是这样」，写明是哪条条件、
依据是什么、动了哪一项。手改过的配额遇到条件调整会**弹一句问你要不要采用**，
而不是静默地让其中一个赢。

**7. 多档案，各有各的日记**
可以新建、切换、删除、修改档案。每个档案一条**独立日记** ——
切换之后首页、日记、健康分、配额全部跟着换。
「清空记录」「恢复演示数据」只作用于当前档案，那一页会点名是哪一个。

**8. 可以对着它说话**
对话页的输入栏有一格麦克风，用的是浏览器自带的语音识别。转写结果**落进输入框**、
不自动发送 —— 中文菜名的识别错误率不低（「清蒸鱼」/「青蒸鱼」），
让人改一个字再发，比把这层错误直接送给模型诚实。
边界和已知限制见[已知限制](#已知限制) —— 这一条在 Firefox 上**用不了**，按钮照常在，
点开会说明为什么。

**9. 慢性病与特殊时期的饮食指导有出处**
对话页挂了一个知识库，内容是**国家卫健委印发的「成人XX食养指南」**（高血压、
糖尿病、高脂血症、痛风、慢性肾病，一份一个病，逐章节转录），加上一份脚本生成的
「食衡自己的配额与依据」—— 后者是唯一知道「App 里勾上高血压，钠会变成 1500mg」
的文档，而它和官方指南的 2000mg 底线是什么关系，也是写明的。
生成、覆盖检查、反向核对都是本机跑得通的；检索本身要等 Dify 那边配完，
状态见[已知限制](#已知限制)。整条的来龙去脉在[路径 B](#路径-b知识库用在对话页)。

### 演示动线

```
首次打开 → 三步建档（或每一步都摆着的「先用演示档案看看」一键跳过）
        → 首页「拍餐盘」 → 拍照/相册 → 分析中（三步） → 确认分量（少/常规/多）
        → 分析结果（可修正分量） → 归档到膳食日记
        → 回首页，健康分变了 → 刷新，还在
```

另外两条：

```
档案页「切换档案」→ 新建第二个 → 切过去（日记是空的，不是第一份的）→ 切回来，记录原样都在
档案页「编辑档案」→ 勾上慢性病 → 回来看到钠变成 1500mg，下面一行写明了为什么
对话页麦克风 → 说一句话 → 文本落进输入框（不自动发送）→ 改一个字 → 发送
```

想看得更细：日记页切「日 / 周 / 月」，日视图可以往回翻日期；
点警示卡对应的那天可以直接跳过去。

## 技术选型：几个值得说的决定

**响应式用 CSS 切换，不用条件渲染。**
`PhoneFrame` 在桌面端画设备外框，在真机上去掉。但如果用
`isDesktop ? <A/> : <B/>` 来切，窗口尺寸一变就会把整棵子树卸载重建 ——
聊天记录、表单里填了一半的内容全丢。所以两套样式都渲染，靠 `sm:` 与
`env(safe-area-inset-*)` 用 CSS 控制。断点用 `40rem` 而不是 `640px`：
Tailwind v4 的 `sm:` 编译出来就是 `@media (width>=40rem)`，
JS 侧用 px 写 `matchMedia` 的话，用户一改浏览器默认字号两边就不同步了。

**底部留白用 `--safe-bottom` 兜底，不要直接写 `env()`。**
`env(safe-area-inset-bottom)` 只在设备真有一根 Home 横条时才有值：iPhone 是
34px，Android 手势条和桌面浏览器一律报 0。直接拿它当底边留白，那些报 0 的
设备上标签栏离屏幕下沿就只剩 14pt、对话页的输入栏干脆贴着边 —— 压进系统
手势区，手指够着别扭，上滑回桌面还容易误触。所以 `index.css` 里统一定义
`--safe-bottom: max(16px, env(safe-area-inset-bottom))`：有横条时让开横条，
没有时也留 16px。桌面上另有覆盖（`@media (min-width: 40rem)` 里改回 0）——
机身外框是我们自己画的，底部那 34pt 是**假的** Home Indicator，
兜底反而会让桌面呈现和设计稿对不上。

**日期用本地时区的 `YYYY-MM-DD` 字符串，不用 `toISOString()`。**
`toISOString()` 会转到 UTC —— 在东八区，晚上 8 点之后记的餐会掉进「昨天」。
这种 bug 在演示时不一定触发，但会在真实使用的第一天就暴露。

**没有状态管理库。**
整个应用一个状态树、不到十个动作，`useSyncExternalStore` 加 40 行就够了。
不上 Redux/Zustand 不是因为它们不好，是这里没有需要它们解决的问题。

**没有 IndexedDB。**
数据量是几 KB。上 IndexedDB 属于为想象中的规模做设计。
但 `persist.ts` 把 `localStorage` 访问包在 try/catch 里 ——
隐私模式、禁用 Cookie 时降级成纯内存模式，而不是白屏。

**Key 必须在服务端。**
见下一节。这件事没有"前端加密"之类的折中方案。

**假数据的边界画在哪里。**
食物成分表是近似值；识别走真模型，但认得多准取决于你的 Dify 应用，
而没有 Key 时会退回本地组菜并**在结果页最上面明说那是演示数据**。
这两件事都在界面上和代码里**明说**了。原因见[已知限制](#已知限制)。

## 接入 Dify agent

对话页已经接好了 Dify 的流式接口，只差填 Key。

**本地开发** —— 在 `private/dify.env` 里填：

```ini
DIFY_API_BASE=https://api.dify.ai/v1
DIFY_API_KEY=app-食衡的key
DIFY_CHAT_API_KEY=app-膳享+的key
```

然后重启 `npm run dev`。改动这个文件需要重启，因为它是在 Vite 启动时读入 `process.env` 的。

**线上部署** —— 在 Vercel 项目的 Settings → Environment Variables 里设同名的三项。

> ⚠️ **是三个变量、两个 Key，别只配一个。** 对话页和识图页接的是**两个不同的
> Dify 应用**，各有各的 Key：
>
> - `DIFY_API_KEY` —— 「食衡」，只给 `/api/recognize`（拍餐盘识图）用
> - `DIFY_CHAT_API_KEY` —— 「膳享+」，只给 `/api/chat-messages`（对话页）用
> - `DIFY_API_BASE` —— 可选，默认 `https://api.dify.ai/v1`
>
> 少配 `DIFY_CHAT_API_KEY` 会**静默退回用 `DIFY_API_KEY`**（见
> `api/_lib/agent.ts` 的 `CHAT_API_KEY`）—— 对话照样能跑、一句错都不报，
> 只是回答来自「食衡」而不是「膳享+」。**这是这个项目里最容易配错的一处：
> 一个不报错的配置错误。**

### 为什么 Key 不能放前端

Vite 的 `VITE_` 前缀**不是**安全机制，只是命名约定 ——
带这个前缀的变量会被原样内联进客户端 bundle，谁都能在浏览器控制台里翻出来。
Dify 的 App Key 一旦泄漏，别人就能直接消耗你的额度。

所以整个链路是：浏览器只请求同源的 `/api/*` → 服务端补上 `Authorization` 头 → 转发给 Dify。
`api/_lib/agent.ts` 是唯一的实现，开发时由 `vite.config.ts` 挂成 dev server 中间件，
生产时由 Vercel 的 Serverless Function 调用。**两边同一份代码**，
避免"本地直连好好的，部署上去发现鉴权头没带上"这种最难查的偏差。

> ⚠️ **上面这句「浏览器只请求同源的 `/api/*`」有一个例外：语音输入。**
> 对话页的语音走的是浏览器自带的 `SpeechRecognition`，它**由浏览器自己**
> 把音频送到识别服务 —— Chrome 送到 Google，Safari 送到 Apple。
> 那条连接不经过本项目的服务端、不经过 `/api/*`、也不经过 `api/_lib/agent.ts`
> 里的限流。这不是可以绕开的实现细节，是"音频离开这台设备"这件事本身，
> 所以在[隐私](#隐私)那一节里也单独列了一条。**要发出去的音频是浏览器管的，
> 我们没有、也拿不到那条链路的开关。**

### Agent 返回的是 JSON，不是文本

**这一点值得单独说，因为它决定了对话页怎么渲染。**

接上 Key 之后做的第一件事是把 SSE 流原样抓下来看。事件是
`workflow_started` / `node_started` / `node_finished` / `workflow_finished`
—— 说明这是个**对话流（Chatflow）**，不是普通 Chatbot。更关键的是
`message` 事件里的 `answer` 字段：它不是一句人话，而是一整段 **JSON 字符串**。

所以原样渲染的话，屏幕上会出现一坨带 `\"` 的原始 JSON。浏览器里长这样：

```
{"blocked": false, "risk": {"level": "low", "message": "午餐摄入钠含量较高…
```

`src/lib/agentReply.ts` 负责把它解析成结构化回复，`AgentReplyCard.tsx` 负责渲染。

**契约不是猜的，是探测出来的**（`npm run probe`）。四种 `mode`：

| mode | 场景 | 结构 |
|---|---|---|
| `plate` | 餐盘复盘 | `dishes[{name, suitable, reason}]` |
| `dish` | 单菜分析 | 同上，另加 `recipe[]` 与 `healthModification` |
| `ingredient` | 知识问答 | 只有 `title` / `advice`，没有 `dishes` |
| `menu` | 食谱、打招呼 | `dishes` 里装的是**整餐**，不是单个菜 |

另有一条独立分支：`blocked: true` 时**根本没有 `result`** ——
这是过敏拦截，风险信息本身就是全部内容。这条分支在渲染层单独处理，
不会去读不存在的 `result`。

`risk.items` **不只是过敏原**。实测同一个字段，拦截分支给 `["花生"]`，
单菜分析给 `["高油、高盐、潜在高糖"]` —— 后者配的 `level` 还是 `low`。
所以它按「风险条目」渲染，配色跟着 `level` 走，不一律标红。
（这正是那种「跑一次样例看不出来、多跑几次才暴露」的问题，
上一版就是无条件用红色徽章渲染的。）

**同一个问题，两次可能返回不同的 `mode`。** 实测「午餐吃了红烧肉和米饭，
有点咸」第一次返回 `plate`、第二次返回 `menu`。`mode` 是模型自己选的，
不是调用方指定的 —— 所以渲染层必须把四种形态全兜住，不能只测一种。
这条也在 `verify:reply` 里锁住了。

**解析器按"对面不守规矩"来写。** 它会加 ` ``` ` 围栏、会在 JSON 前后裹一句
「好的，以下是分析结果：」、会漏字段、会把 `items` 给成字符串而不是数组。
任何一步失败都返回 `null`，由调用方退回渲染纯文本 ——
**难看总好过看不到**。这个取舍贯穿整个接入层，和下面的降级策略是同一个原则。

改了 Dify 里的 prompt 或换了模型之后，跑 `npm run probe` 确认前端还认得新输出。

### 让 agent 读到你的健康档案

**问题**：这个工作流原本只声明了 `sys.*` 变量（`sys.query` / `sys.files` /
`sys.user_id` / `sys.dialogue_count`），所以 agent 不知道你在档案页填了什么。
它只能根据你**在对话里说的话**给建议 —— 实测过：只有你明说「我对花生过敏」，
它才会拦截；档案里写着的花生过敏它读不到。给出的建议因此全是
「若处于控糖或高血压阶段…」这种两边都不得罪的说法。

**做法**：App 每次提问时把档案和当天摄入**塞进 query 的 JSON 里**发过去
（`src/lib/agentContext.ts`）。构造出来的东西长这样：

```json
{
  "profile": {
    "basicInfo": { "age": 28, "gender": "女", "heightCm": 165, "weightKg": 55 },
    "healthGoals": ["salt_control", "balanced", "sugar_control"],
    "healthRestrictions": [{ "item": "花生", "type": "allergy", "severity": "high" }]
  },
  "todayIntake": {
    "date": "2026-09-19", "time": "14:30",
    "meals": [{ "slot": "早餐", "slotCode": "breakfast",
                "items": [{ "name": "燕麦粥", "grams": 300 }] }],
    "total": { "kcal": 1579, "protein": 93, "sodium": 2465, "...": 0 },
    "quota": { "kcal": 1800, "sodium": 2000, "...": 0 },
    "missingSlots": ["晚餐"]
  },
  "input": { "text": "晚餐吃什么好？", "images": [] }
}
```

#### 为什么不是「输入变量」

这一点我最初理解错了，值得写下来，因为它反过来正是这份工作流的设计：

Dify 的 `/parameters` 里确实声明了一个 `user_context` 变量 —— 但**整个工作流
没有任何一个节点引用它**。往 `inputs` 里塞多少东西都进不了提示词，而且
Dify 对未声明的输入变量是**静默丢弃**的（实测：请求照样返回 200）。
于是那条路上有一个「看起来通了、其实什么都没发生」的陷阱。

真正在传档案的是 `sys.query`：节点 2 拿它做 `json.loads`，解出来的 `profile`
喂给节点 7 的过敏原拦截和 LLM 节点的提示词。所以发纯文本提问时：

- `json.loads` 失败 → 节点 2 走 `except` 把 `profile` 置空 → **不报错**
- 结果是「读档案」和「过敏原拦截」两层同时失效

实测：档案里写着花生过敏，用纯文本问「晚餐吃什么好？」，照样能拿到建议。

#### 两个字段口径必须对齐

这两条错了，拦截会**静默失效** —— 不报错、看不出哪里不对，只是永远不拦：

| 字段 | 必须是 | 不能是 | 为什么 |
|---|---|---|---|
| `healthRestrictions[].item` | `花生` | `花生过敏` | 工作流判命中的写法是 `if item in haystack` 这种子串匹配。`"花生过敏" in "我吃了花生"` 是 `False`，过敏原拦截在最该触发的时候不触发 |
| `healthRestrictions[].severity` | `high` | `高危` | 节点 7 判的是 `r.get("severity") == "high"`，中文字面量永远不等于它 |

`verify` 里各有一条断言专门盯着这两条，因为它们出错时不会有任何报错。

`healthGoals` 同理映射成枚举码（`控盐` → `salt_control` 等）；
**认不出的目标原样保留**，不丢弃也不猜一个最近的码 ——
「备孕」是真信息，模型读中文毫无问题，硬映射成 `balanced` 才是编造事实。

#### 工作流要改的三处

**① 节点 7 —— 必改，这条是 bug**

节点 7 的后置校验扫的是 `json.dumps(result)` **全文，连 `advice` 一起扫**。
于是给一个花生过敏的人写「避免花生」这条正确建议，反而会被判定命中并拦截 ——
**越是需要建议的人越拿不到建议**。

而且它是**不确定的**，这一点是同一轮探测里抓到的：同一条「晚餐吃什么好？」，
作为对照 A 被拦截，几秒后在同一批请求里又正常给了建议；「膳食纤维有什么作用？」
这种纯粹的知识问答也时拦时不拦（见下面的探测输出）。所以不是「偶尔难看」，
是「演示时有大约一半概率突然说已拦截」。

把 `if not blocked:` 里构造 `haystack` 的那两行换成：

```python
        nut = result.get("nutrition") or {}
        haystack = json.dumps({
            "dishes": [d.get("name") for d in (result.get("dishes") or []) if isinstance(d, dict)],
            "ingredients": [i.get("name") if isinstance(i, dict) else i for i in (result.get("ingredients") or [])],
            "nutrition_ingredients": nut.get("ingredients") or [],
            "riskItems": nut.get("riskItems") or [],
        }, ensure_ascii=False)
```

只扫「用户真的会吃进去的东西」，不再扫 `advice`。

**② 节点 2 —— 多返回一个 `text`**

```python
    return {"blocked": blocked, "blocked_json": blocked_json,
            "blocked_items": blocked_items, "text": text}
```

然后在节点 2 的「输出变量」里加 `text`（String）。

**③ 节点 5 —— 检索文本换掉**

查询文本从 `用户输入.sys.query` 改成 `代码执行.text`。否则 query 变成 JSON 后，
检索词里会混进 `healthRestrictions`、`severity` 这些字段名，稀释 RAG 命中率。

改完点**发布**。

#### 开关的来历

`SEND_PROFILE_TO_AGENT`（在 `src/lib/agentContext.ts`）现在是 `true`，
App 每次都把档案塞进 query 发出去。

它一开始是 `false`：上面那个节点 7 的 bug 没修之前，打开它演示会变成
「问什么都已拦截」，比不开更糟。上游修好之后先跑了稳定性验证才打开的 ——
**应当放行的 6 次全部放行，应当拦截的 2 次全部拦截**。

如果你换了一个没修过这个 bug 的 Dify 应用，把那一行改回 `false` 即可：
App 退回发纯文本，agent 读不到档案但仍然可用，不会白屏。
`verify` 里有一条断言盯着这个开关的值，改它会红，提醒你回来看这段注释。

#### 怎么确认配好了

跑 `npm run probe`。它做的第一件事是一对**对照实验**，两句都发结构化 JSON：

- **对照 A（不该拦）**：「晚餐吃什么好？」—— 这句话里没有「花生」二字，
  正常应该给出建议。若返回已拦截，就是上面那个节点 7 的 bug。
- **对照 B（该拦）**：明说刚吃了含花生的菜。这一条不拦，问题就不是误拦，
  而是拦截压根没生效（多半是 `item` / `severity` 口径没对齐）。

A 拦了、B 没拦，都是坏消息，而且指向不同的地方。两个都对，才会打印
「可以打开 `SEND_PROFILE_TO_AGENT` 了」。

> 这个脚本**始终**按「档案已接通」的方式发 JSON，不管 App 里那个开关是开是关 ——
> 它的用途就是提前验证上游改好没有。

#### `todayIntake` 现在是死的

上面那段 JSON 里的 `todayIntake` 目前**发过去没人读**：节点 2 只挑它认识的键，
这个会被丢掉。保留它是因为用户问「今天盐吃多了吗」时 agent 确实需要这些数字，
而接上只需要在工作流里加两行：

1. 节点 2 的 `return` 里再加一个 `"today_intake": json.dumps(today_intake, ensure_ascii=False)`
   （节点 2 已经有解出来的对象，直接透传即可），并在输出变量里加 `today_intake`（String）。
2. LLM 节点的提示词里加一行 `{{#代码执行.today_intake#}}`。

发一个暂时没人读的字段，比以后再改一次 App 划算。

**为什么只发健康相关的字段。** 档案里还有 `name`，但它对营养推理没有任何用处，
发出去只是把一条身份标识交给第三方。年龄、性别、身高体重是算营养必需的，那些发。
这条线画在「推理需要」而不是「档案里有」—— `verify` 里有一条断言专门盯着它，
而且是拿一个绝不可能出现在别处的标记字符串去测的（否则测了等于没测）。

**特殊时期 / 慢性病 / 饮食偏好现在会发。** 这三项以前是「档案页没有对应输入，
所以不发」（与其编一个空值让工作流以为你填了，不如不发），档案页补上这三项之后
它们进了 `profile`：

```json
{
  "specialStage": "孕期",
  "chronicConditions": ["高血压"],
  "dietaryPreferences": ["素食", "低GI"]
}
```

取值用**中文**，这是刻意的，也是这一节里唯一一处还需要你确认的地方 ——
本文件里两套口径的先例正相反（`item` 是中文裸词因为模型直接读，`severity`
是英文枚举因为节点 7 在做 `== "high"` 的代码比较）。这三个字段归哪一类，
取决于工作流里引用它们的那个节点是**插值引用**（`{{...specialStage}}`）还是
**代码比较**（`if stage == "pregnancy"`）：

- 插值引用 → 现在这样就对了，中文原样发，模型读中文毫无问题
- 代码比较 → 需要在 `agentContext.ts` 里加一层映射，位置就在
  `GOAL_CODES` / `SEVERITY` 旁边，**改动只落在那一处**

`specialStage: "无"` 和空数组都照发：它们是这个枚举里**真实取值**（用户答的就是
「没有特殊时期」「没有慢性病」），不是「没填」的占位 —— 和一直这么发的
`healthRestrictions: []` 保持一致。真正要避免的是**编**一个值。

> ⚠️ **`specialNutrition` 故意不发。** 它是工作流里唯一一个连**语义**都猜不出来的
> 字段：指的是「这个阶段带来的营养增量」（一个数）还是「这个阶段的营养原则」
> （一段文字）？形状猜错的表现是模型把它当成了另一种东西，然后在回答里编出
> 一套数字 —— 而且不报错。等确认了形状再加。

`verify` 里对这三个键的断言是**双向**的：填了必须发、没填不能编。
（它以前是一条「这三个键不许出现」的禁令 —— 那条禁令的用意是「与其编一个空值，
不如不发」，档案页补上之后它升级成了口径正确的守卫，用意没变。）

### 降级是主路径，不是兜底

打开这个链接的人没有你的 Key。所以「没有 Key」不是故障，是**预期内的正常状态**：

| 情况 | 行为 |
|---|---|
| 配了 Key | 真实 agent 流式回答，解析成卡片 |
| 没配 Key | 顶部挂一条说明，回答由本地规则结合**你的真实记录**生成 |
| 限流 / 超额 / 报错 | 提示具体原因，切到本地回答，界面照常可用 |
| agent 返回的解析不了 | 原样显示文本，不白屏也不留空 |
| 刷新在结果页 | 给出明确的空状态和返回入口，不白屏 |

流式期间**不渲染半截内容**。既然回答是一整段 JSON，边收边渲染就会先闪一坨
原始 JSON 再变成卡片 —— 所以先攒完整段再解析，等待期间只显示三点动画。
反正这个 agent 是把答案攒在一个 `message` 事件里一次性发出来的，逐字渲染也没有意义。

演示模式的回答刻意**不是**一段预置文案 —— 它按关键词命中规则，
再用当天实际摄入和档案配额算。问「今天盐吃多了吗」和「热量还剩多少」会得到不同的、
带真实数字的回答。

服务端还带了按 IP 的滑动窗口限流（每分钟 12 次），
避免这个公开链接被人拿去刷额度。这是尽力而为的防护，不是严格配额：
Serverless 会横向扩实例，每个实例各记各的。目标是抬高滥用成本。

### 拍餐盘的真实链路

首页的「拍餐盘」不是装饰：选中的照片真的会被送去多模态模型识别，出来的菜品、热量、
建议都是从那张图算的。**但"唤起相机"这件事各平台行为不一样**，先把话说清楚：

| 平台 | 相机图标 | 相册图标 |
|---|---|---|
| **Android Chrome** | `capture="environment"` 真的直接打开相机 App | 打开相册 / 文件选择器 |
| **iOS Safari** | 弹 iOS 自己的单子（拍照 / 照片图库 / 浏览文件） | **同一个单子** |
| **桌面浏览器** | 忽略 `capture` → 文件选择器 | 文件选择器 |

iOS 上 `capture` **不能强制**进相机 —— 只要 input 收图片，iOS 就会弹那张单子，
`capture` 只是「优先后置」的提示，既不能强制进相机也不能把相册那一项去掉
（WebKit Bug 236981 里就是这么写的）。所以**这两个按钮的差别只在 Android 上成立**。
要三端一致地「真的打开相机」，只有 `getUserMedia` 那条路，代价见[已知限制](#已知限制)。

```
点拍照 / 相册 ──▶ <input type="file" accept="image/*" capture="environment">
                     │  选中的 File
                     ▼
               image.ts  解码 → canvas 缩到长边 1024 → JPEG q0.8
                     │
                     ▼
        POST /api/recognize     multipart: 图 + user + query JSON
                     │
        服务端串起 Dify 的两步（浏览器只发一次请求，Key 不出服务端）：
          ① POST {dify}/files/upload                    → upload_file_id
          ② POST {dify}/chat-messages
             files: [{ type: 'image', transfer_method: 'local_file',
                       upload_file_id }]
                     │
                     ▼
        SSE 原样透传 ─▶ parseAgentReply ─▶ matchDishes ─▶ 结果页
```

**图片不走 query。** `agentContext.ts` 里有个 `images?: string[]`，那是接图之前
「把图片 URL 塞进 JSON 一起发」的猜测，已证明是错的：Dify 的图片走 `chat-messages`
的 **`files` 数组**，和 query 是两条独立通道。往 query 里塞 URL，模型一个字都看不到 ——
工作流的 LLM 节点只认 `sys.files`。那个字段现在恒为 `[]`，注释里写死了这件事。

**Dify 侧有两项必须先开，否则前端写了也白写：**

| # | 做什么 | 在哪 |
|---|---|---|
| 1 | 开启**图片上传** | 应用编排页右上角「功能」→ 打开「图片上传」 |
| 2 | LLM 节点开启 **VISION**，图片来源选 `sys.files` | 编排页点开那个 LLM 节点 → Vision 开关 |

第 2 条是社区里报得最多的配置遗漏：**不开 Vision 的话图片照样能上传、请求也 200，
但模型看不到图**，于是它会照着 query 里的文字编一份格式完全正确的菜品清单 ——
输出挑不出毛病，唯一的问题是它压根没看过那张照片。

**这两项当前都是开着的**，不是推定，是量出来的（`npm run probe:vision`）：
第 1 步 Dify 收下文件并返回了 `upload_file_id`（接口层开关是开的）；
第 3 步从一张真实餐盘照里认出了 `清蒸鱼 / 白灼西兰花 / 米饭(熟)` 三道菜 ——
**看不见图时模型只会回「无法识别食物图片」+ 空 `dishes`**，所以认得出真菜名只有"看见了"一种解释。

> 这个探针原本用第 2 步的一对**对照实验**当判据：同一句「这张图是什么颜色？」配一张纯品红方图和不配图，品红是刻意挑的（餐盘照片里不会自然出现），所以图的颜色一改输出就是「看见没看见」的是非题，比「识别得像不像」确定得多。
>
> **但这一步后来失效了**：agent 的人设是饮食决策助手，面对这个无关问题会直接回「超出服务范围」——拒绝与否和看不看得见图**无关**，于是它得不出任何结论，而且**每次都会亮红**。一个恒亮的红灯比没有红灯更糟：人会学会无视它，哪天真的没开 Vision 也照样被无视。所以判据挪到了第 3 步，第 2 步只保留两种仍能定性的情形（模型说看不到图 / 带图和不带图一字不差），其余一律报「不确定」并指向第 3 步。

> 顺带记一个查了半天才明白的坑：这个工作流第一步是 `json.loads(sys.query)`，
> 所以**纯文本提问会走它的 `except` 分支，返回 HTTP 200 + 「本次生成结果解析失败，请重试」**。
> 看着像上游挂了，其实是 query 的格式不对。排查时分三层看：
> HTTP 非 2xx 是接口层拒绝（没 Key / 限流 / 图片被拒）；200 + 那句兜底文案是 query 不是
> 工作流要的 JSON；200 + 结构化回复才是走到了模型。`probe:vision` 会把这三层分开报。

**为什么一定要重新编码成 JPEG。** 一次 canvas 缩放同时解掉三个约束：

| 约束 | 不管它会怎样 |
|---|---|
| iPhone 拍出来是 **HEIC**，而这个 Dify 应用的 `allowed_file_extensions` 里没有 HEIC | 上传被拒，且 Dify 是**按扩展名字符串**判的，不看文件真实内容 |
| 手机原图 3–8MB | 超过 Vercel serverless 约 **4.5MB** 的请求体上限 |
| Dify 图片上限 10MB | 同上 |

服务端还会按 MIME 把文件名重写成 `plate.jpg` —— 客户端那张可能叫 `IMG_1234.heic`，
照抄名字会让一张正常的 JPEG 因为名字被白名单拒掉（这条有断言盯着）。

**照片只留一张缩略图。** 完整的那张只活在内存里当预览图（object URL，刷新即丢）；
归档时另外生成一张 200px / q0.6 的缩略图（约 8–12KB，base64 后约 11–16KB）存进
`MealEntry.thumb`，日记列表里显示的就是它。配额账：14 天演示数据 × 3 餐 × 16KB ≈ 670KB，
5MB 配额下安全。

但这个决定有个必须同时处理的隐患：`persist.ts` 的 `saveState` 原来**静默吞掉所有异常**。
塞进 data URL 之后，配额写满就从理论问题变成会真实发生的事，而**失败是无声的** ——
用户刚记的一餐看起来存好了，刷新就没了。所以现在：

- 写失败会冒泡到界面（「我的」页顶部一条提示，那里的清理按钮正好是自救入口）
- 写失败时**去掉所有缩略图重试一次** —— 营养数据是可贵的，照片是可弃的，
  不能因为一张图把整餐记录写没。重试成功会明说「已保存营养数据，但没存下 N 张照片」。
  多档案之后缩略图散在 `state.meals` 和 `state.profiles[i].meals` **两处**，
  重试要剥的是两处：只剥当前档案的话，那张碍事的照片在**别的档案**里，
  用户看到的是「存储空间不足，这一餐没能保存下来」，怎么看都跟眼前这一餐没关系
- 两次都失败才报错，并指路去清理旧记录

`npm run verify:quota` 用一个能精确控制容量的假 localStorage 把这三条路径都跑了一遍，
最硬的那条断言是「**营养数据完整落盘**」。

**限流是拍照和聊天共用的**（每 IP 每分钟 12 次）。一次拍餐盘在浏览器看来是**一个**请求，
所以只扣**一个**令牌 —— 尽管服务端为它上游调了两次 Dify（上传 + 对话）。
两者共用一个额度桶是故意的：图片那条路贵得多，单独给一份额度等于开了个不用排队的后门。

**识别结果里有两类「没有菜」，含义完全不同**，界面分别对待：

| 情况 | 界面怎么说 | 下面那些菜是哪来的 |
|---|---|---|
| 请求没到模型（没 Key / 断网 / 超时） | 「以下菜品为演示数据，不是识别结果」 | 本地随机组的，和照片无关 |
| 模型看过图了，但没认出菜 | 「这张图里没认出菜品」+ 模型的回答原话 | 没有菜，给出重拍 / 手动记录两条路 |

混成一句就会出现「演示数据」配一张真实照片这种自相矛盾的界面。
第二种是实测会走到的：拿一张纯色方图跑真实链路，模型回「未知菜品 (图片无法识别)」——
它答对了，那张图里确实没有菜。

### 确认分量那一步

分析完、出结果之前，中间夹了一屏让你确认每道菜的份量。

**这一屏是补上一个说不通的地方。** 结果页原来每道菜写「**估算** 150g」，
但那个 150 既不是从照片里推出来的，也不是模型给的 —— 它是 `data/foods.ts` 里
`rice.defaultGrams` 这个**常量**。界面用「估算」这个词，把一个常量说成了推断结果。
而这个仓库其它地方都在防同一件事：演示数据要标出来、认不出的菜要显式按 0 计、
宁可删掉 `confidence` 也不编一个数。一个**没有出处的数字**比一个明确的「不知道」更糟。

**从一张照片估出重量这件事做不到**，所以没去让模型猜得更准，而是把它交还给唯一知道
答案的人 —— 而且只问他答得出来的那个问题：

| | |
|---|---|
| 三档 | 少量 0.6× / 常规 1× / 多量 1.5×，乘完取整到 5g |
| 为什么不让填克数 | 没人知道自己那碗饭是 180g 还是 250g。逼着填只会换来一个**看起来很精确的错数字** —— 正是要消灭的那个东西。能答出来的是「大份还是小份」 |
| 必经还是可跳 | 必经，但**默认全部「常规」**，所以快速路径就是进来直接按主按钮 |
| 「常规」是多少 | 真实路径上**就是这道菜当前的克数**（普通情况下等于食物库的常见分量），演示路径上是食物库的默认值 |

「常规」的基准分两条路，各有一个必须守住的理由：

- **真实路径用当前克数**，因为那是唯一能保住两种有信息量的克数的选择。一是**合并过的菜**：
  `matchDishes` 把落到同一个 `foodId` 的两道菜相加（「白灼西兰花」+「清炒西兰花」→ 西兰花 300g），
  拿默认值当基准的话，用户随手点一下「常规」就会把它静默砍回 150g —— 一次没有提示的数据改写。
  二是**将来模型真的开始给克数**：`dishMatch` 支持可选的 `grams` 字段，README 也承诺过
  「提示词加了 App 不用改」，那这条承诺得守住。
- **演示路径用食物库默认值**，因为那条路的克数是本地在默认值上 ±15% 抖动出来的**噪声**。
  拿噪声当基准，「常规」就变成一个每次都不同的随机数：同一盘菜照两次给出两个克数，
  用户只会认为这个 App 在乱来。

于是有一条可以断言的不变量：**真实路径上、且没有发生合并时，点「常规」不改变任何数字**
（`npm run verify` 里有这条）。它成立得比看上去稳 —— `matchDishes` 已经把克数取整到 5g 了，
所以取整在「常规」这一档是个恒等变换。

**三种情况会跳过这一屏**，判据收敛成一条 `countableItems(items).length === 0`：
模型说没认出菜、认出的菜全不在食物库里、过敏拦截（拦截分支的 `dishes` 是空的）。
没什么可称的时候摆一个空步骤只是让人白点一次。

**降级路径也走这一屏**，所以它同时受两条约束：要挂「演示数据」横幅，且**不显示用户拍的那张照片**。
`plate.ts` 在降级时刻意没把 `photoUrl` 放进结果，理由正是「把真照片摆在编出来的菜旁边，
等于暗示这个因果关系」—— **这一屏不能把那个漏洞重新开出来**。

未收录的菜会列出来但**不可点**（注明按 0 计）。不列的话，用户拍了三道菜只看见两行，
会以为 App 漏了一道。

（三档控件复用 `ui/SegmentedControl`，但给它补了两样东西才敢用在必经路径上：
一个 **44pt 的尺寸档**（原来那档三个相邻目标只有 26pt、间隔 2px，是误触发生器），
以及**一组 ARIA**（`radiogroup` + `radio` + `aria-checked` + 方向键 + roving tabindex）——
改之前它选中状态只靠背景色传达，读屏用户在一屏里听到几组没有选中态的按钮，
分不清在哪一行。）

### 让模型从食物库目录里挑（以及知识库该用在哪）

这一节回答「怎么再丰富一点知识」，同时说清楚**哪条路不该走**。

#### 三件事，三套办法

| 想达到的效果 | 用什么 | 为什么 |
|---|---|---|
| **让「按 0 计」变少** | **提示词里加食物库目录** | 这是个**封闭集合**的选择题：有标准答案、可校验。58 条目录只有 700 token，塞进提示词毫无压力 |
| **让对话页答得更好** | **知识库** | 那是开放问题，答案是一段给人看的话，不进任何数据结构 |
| **让模型直接报出营养数字** | **不做** | 那些数字会进日记和健康分。模型每次现编的数没有出处、不可复现，见[已知限制](#已知限制)里那条 |

判据其实只有一条：**这个数字会不会进日记和健康分。** 会，它就必须有出处、可复现、可校验；不会，用什么办法都无所谓。

#### 路径 A：提示词里加食物库目录（推荐，且 App 侧已经支持）

```bash
npm run catalog        # 从 data/foods.ts 现读，生成 dify/catalog-prompt.txt
```

生成的文件里是一段**可以直接粘贴**的文本：58 条 `foodId=名字` 按分类排好，后面附四条给模型的规矩。然后：

1. 打开 Dify → 你的工作流 → 那个负责识别餐盘的 **LLM 节点** → 提示词
2. 把这段粘到**输出格式说明的附近**（要紧挨着描述 `dishes` 数组字段的那几行，
   否则模型容易当成无关背景忽略掉）
3. 保存 → 回到本项目跑验证：

```bash
npm run dev            # 另开一个终端
npm run probe:vision   # 发一张真图给真 Dify
```

看这一行：

```
  目录命中:模型自己挑了 N/M 个 foodId
```

- **N/M 是 0**：改动没生效。先查是不是贴到了别的节点上；再查提示词里有没有明确
  写「必须从目录里挑」——不说这句，模型会照旧自由发挥
- **生效之后**：`匹配:` 那一行的落空会明显减少，探索性那句话也会消失

**2026-09-19 实测：这条路由 3/3 全中走通了**，落空 0 项：

```
  ✓ mode=plate  risk=low  3 菜
     · 清蒸鱼 [适宜]  ← 模型自己挑了 steamed-fish
     · 白灼西兰花 [适宜]  ← 模型自己挑了 broccoli
     · 米饭(熟) [适宜]  ← 模型自己挑了 rice

  目录命中:模型自己挑了 3/3 个 foodId
  匹配:3 项进库 / 0 项按 0 计
```

**注意这个探针报「Vision 开没开」的位置。** 它原本用「发一张纯品红图、问它什么颜色」做对照实验，但**人设把这一步废掉了**：面对「这张图什么颜色」，饮食决策助手会直接回「超出服务范围」——拒绝与否和看不看得见图无关。所以现在判据放在**从真实餐盘照里认出真菜名**：看不见图时模型只会回「无法识别食物图片」+ 空 `dishes`（探针第 2 步的无图对照组当场演示了这个），所以认得出真菜名只有"看见了"一种解释。

顺带记一条经验：那个对照实验之前**每次都会亮红**。**一个恒亮的红灯比没有红灯更糟** —— 人会学会无视它，哪天真的没开 Vision 也照样被无视。所以现在它报「不确定」并指向第 3 步，而不是报错。（同一类问题的另一面见[自检脚本](#自检脚本)里那条「假装通过的断言」。）

**为什么用提示词而不是知识库。** 58 条数据用 RAG 是**拿一个不可靠的检索去换一个可靠的查表**：检索没命中，模型就认为目录里没有这道菜，直接落空。知识库的价值在「文档多到塞不进提示词」的地方，而这里离那个量级差三个数量级。

**为什么不让它顺便估克数。** 字段是支持的（`DishInput.grams`），但我们的提示词**故意不要**：从一张照片估出重量这件事做不到，这正是[确认分量那一步](#确认分量那一步)存在的理由。库里的值都是「每 100g、熟食、可食部」，所以只要挑对了菜，克数交给用户按大份小份确认就够。

#### 路径 B：知识库（用在对话页）

对话页的回复是散文，`/chat` 那条路不进任何数据结构、不参与健康分，**挂知识库没有任何风险**，而且那里检索确实是唯一可行的办法。

**内容这一半已经做完了**（链路那一半还没通 —— 检索要等 Dify 那边配完才算数，见[已知限制](#已知限制)里那条）。知识库内容是**国家卫生健康委办公厅发的「成人XX食养指南」**，一份一个病，逐章节转录成结构化 Markdown（来源与整理规范在 `knowledge-base/`，那个目录不进仓库，理由见 `.gitignore` 里的注释）。

##### 内容分两半，界线划在「谁知道这个数」上

| 来源 | 内容 | 为什么是它 |
|---|---|---|
| **官方指南原文**（10 份） | 食养原则、食物选择、食物交换表、地区食谱、食养方、嘌呤含量表 | 权威。这些是印发文件，不是我写的科普 —— 知识库最坏的失败不是答不出来，是**答得像模像样但是错的** |
| **脚本生成**（5 份） | `00 口径与范围`、`01 食衡的配额与依据`、孕期/哺乳期/更年期 | 官方指南**不知道食衡是什么**。`01` 讲的是「在食衡里勾上某个条件之后那八个数字变成多少、依据是什么」，只有这个 App 自己答得出来 |

分界线不是审美。官方指南写「高血压患者每日食盐逐步降至 5g 以下」（约合钠 2000mg），而食衡里高血压的配额是**钠 1500mg** —— 两个数不一样，而且都对。没有 `01` 那一份，模型拿到两个数只能自己猜哪个算数；有了它，关系是写明的：*「App 里的 1500mg 比这条底线更严，是 App 自己取的目标值，回答时不要把 1500mg 说成指南的要求。」*

##### 跑法

```bash
mkdir -p knowledge-base/processed   # 把转录好的官方指南 .md 放这里
npm run kb                          # → dify/knowledge/（15 份）
```

`npm run kb` 做三件事：读 `knowledge-base/processed/*.md`、生成上面那 5 份、把 15 份一起写进 `dify/knowledge/`。**导入 Dify 时整个文件夹一起传**，不用挑。

它同时是一道闸门 —— 覆盖检查没过就**不生成文档**：App 里每个慢性病都得配上官方指南（病名对不上要显式映射，见下），每个特殊时期都得有自己写的那一节，每条「官方指南怎么讲」都要回原文核对引文还在不在。少一章的知识库比没有知识库更糟：检索不到的时候，没有任何人会知道。

##### 两条自律，都是为了不出现「两套说法」

**一、凡是和 App 重叠的数字，必须从 `quotaFor()` 现读，一个字都不手抄。**

手抄一份的结局能预演：文档写「高血压每日钠 <2000mg」而 App 里是 1500mg —— 同一个 App 自己打自己的脸，而且是两处都写着出处、都看起来对的那种。这和前面警告过的「对话页说一套、拍餐盘算一套」是同一个失败，换了个方向。

所以 `01` 里每个数字都是从 `quotaFor()` / `quotaNotes()` 现算的，连「依据」那段话也是 `quotaNotes().basis` **原样**取出来的 —— 那份字符串就是档案页「这些数字为什么是这样」印的同一份，于是文档和界面**不可能**说出不同的话。生成之后还会**从写出去的文件里反向读回**钠值再和算法比一次（断言在 `make-kb.mjs` 里：*「从生成物读回，不是断言代码里写了 1500」*——后者是自证）。

**二、病名对不上是静默的，所以映射必须显式。**

App 里叫「高血脂」，官方指南叫「高脂血症」；App 里叫「痛风」，它叫「高尿酸血症与痛风」；App 里叫「慢性肾病」，它叫「慢性肾脏病」。拿 `disease === condition` 去 join，**一条都匹配不上，而且不会报错** —— 只会生成一份少了五章的文档。所以映射是手写的 `CONDITION_DOC`，并且双向校验。

##### 验证：证据是单向的

```bash
npm run dev        # 另开一个终端
npm run probe:kb
```

**先说清楚这个探针证明不了什么**，因为这比它测什么更要紧：慢性病饮食建议是公开常识，一个没接知识库的模型也答得出来，而且答得很像样。所以——

- **答对 ✗ 不能证明知识库生效了**
- **答错 ✓ 能证明知识库没生效**

证据是单向的，脚本因此只在一个方向上给确定结论，另一个方向老实报「不确定」。

它问四件事：两个**只有文档里才有**的问题（「食衡给高血压用户设的钠上限是多少」——1500 是 App 自己取的数，公开语料里不存在；「食衡的配额里有嘌呤这一项吗」），两个 `00` 号文档**点名不收**的问题（用药、诊断），看它会不会硬答。

**决定性证据不在脚本里，在 Dify 的运行日志里**：打开那一轮对话 → 点开检索节点 → 看命中了几条、命中的是哪几份文档。命中 0 条而模型答得像样 = 它在凭常识答，知识库白接了。这跟 `probe-vision.mjs` 那条教训是同一个形状：**一个恒亮的绿灯比没有绿灯更糟**，所以宁可打印「不确定」。

##### 工作流那边要改的一处

检索节点的查询文本从 `用户输入.sys.query` 改成上游「代码执行」节点的 `text`。`sys.query` 现在是档案 JSON，不换的话检索词里混进 `healthRestrictions`、`severity` 这些字段名，会把命中率稀释掉。

##### 剩下的三步（在 Dify 界面上，不用改代码）

| 步骤 | 做什么 | 该注意的 |
|---|---|---|
| 分段设置 | 一条一个知识点 | 官方指南本身已经按章节转录，按标题切就够 |
| 索引方式 | 有 embedding 就用「高质量」 | 没有就选「经济」，中文效果会差一些 |
| 检索设置 | 先用「混合检索」+ Top K 3～5 | `score 阈值`先别开，等看到实际召回再调 |

##### 如果换一批文档进来

**最难的一步从来是内容，不是配置。** 知识库的质量上限就是喂进去的文档的质量：

- **喂结构化数据（CSV / API 导出），别喂 PDF 表格。** 中文营养表的 PDF 解析是出了名的差 —— 生熟两栏、合并单元格、每 100g 与每份混排，检索出来的很可能就是**错行**（这也是那 10 份指南是逐章节**转录**、而不是直接把 PDF 丢进去的原因）
- **口径要跟着文档一起喂进去。** 在文档开头写清楚「本文所有数值为每 100g 熟食可食部」。不写的话，对话页引用的可能是生食材或每份的值 —— 于是又回到「对话页说一套、拍餐盘算一套」
- 免费可用的来源：USDA FoodData Central（有免费 API，结构化、每 100g，但美式食物多），国内公开的营养数据集。商用数据库（如《中国食物成分表》电子版）要看清授权范围
- **转录官方指南时顺手把数字对一遍 App 的算法。** 这次就靠这个抓出三个我自己的错：糖尿病那条原写成「膳食指南区间 50%~65%，45% 是自设的更严格目标」，而官方指南（2023 年版）给的区间是 **45%～60%** —— 45% 就是官方下限；慢性肾病那条也只写了「0.8 g/kg」，而官方是按分期给的（1～2 期 0.8、3～5 期 0.6），**且都用理想体重（身高 − 105）计**，App 用的是实际体重。两处都改成了引用手上这份文件

#### 这条路 App 侧差点白改一场

值得记一笔：上面这套流程第一次做的时候**没有任何效果**，而且不报错。

`matchDishes` 一直支持可选的 `foodId`（还有自检断言盯着），但那个字段从 Dify 回来之后要穿过三层，**其中两层都在悄悄把它丢掉**：

```
Dify 的 JSON ──▶ parseAgentReply 把项映射成 5 个字段     ← 这里丢了 foodId
              ──▶ recognizeAgent 又只取 { name }         ← 又丢了一次
              ──▶ matchDishes({ name })
```

表现是：**你在 Dify 那边加好了目录，App 这边什么都没发生，也没有任何报错。** 这也解释了一个反直觉的现象 —— 项目里那两条断言（「模型报的合法 foodId 直接用」「模型编的 foodId 被拒」）一直是绿的，因为它们直接调 `matchDishes`，**根本没走那条真实链路**。

现在通了，并且加了一节走**整条客户端链路**的断言（`scripts/verify-reply.mjs` 的「模型自己挑 foodId」），喂的是写死的 SSE，测的就是上面这三层。

## 自检脚本

不喜欢"跑起来点两下看着没问题"这种验证方式，所以关键逻辑有七份可重复执行的检查
（`npm run verify:all`，一份失败就整体失败，目前 **586 条断言全绿**）：

**`npm run verify`** —— 闭环自检。用 Node 直接跑 store 的派生逻辑：

- 种子数据落在今天、健康分在 0–100
- 200 次随机识别都出菜、foodId 全部有效、营养值有限
- **归档一餐后，餐数 +1、热量增加**
- **把钠上限从 2000 调到 1200，健康分确实下降**
- 空记录、未知 foodId、空菜品列表不崩
- **幽灵条目探测器「会响」而且「不乱响」** —— 这两条缺一不可：只会不乱响的探测器
  是个永远不报警的摆设（加了比没加更糟，因为它让人以为这条已经有人管了），
  而会乱响的探测器（把 `unmatched:` 哨兵也算成幽灵）会让真警报被淹没。
  另有两条边界：同一道菜出现在三餐里合并成一条且 `count` 累计；**种子数据零幽灵**
  （所以这张卡在演示里不会平白出现）
- **食物库没有重复 id** —— 重复 id 会让 `FOOD_BY_ID` 少一条（`Map` 后写的覆盖先写的），
  而「删掉重复项」这个修正动作正好会制造幽灵条目。护栏留在源头更便宜
- **发给 agent 的那段 JSON 是合法的** —— 工作流要 `json.loads` 它，格式错了
  整个档案就静默失效
- **忌口的 `item` 是裸词「花生」而不是「花生过敏」**，
  **`severity` 是 `high` 而不是「高危」** —— 这两条错了拦截会静默失效、不报错
- **发给 agent 的数字和界面上同源**：拿 `dayStats` 的钠值反算一遍，
  确认发出去的确实是算出来的，不是手写的
- **整段 JSON 里不含档案姓名** —— 断言之前先把档案名换成一个不可能撞车的标记串，
  否则这条测试是自欺欺人
- **认不出的健康目标原样保留**，不被丢弃也不被猜成别的码
- **`SEND_PROFILE_TO_AGENT` 现在是 `true`** —— 这个开关在节点 7 的 bug 修好、
  跑过稳定性验证之后才打开的（那段经过在[让 agent 读到你的健康档案](#让-agent-读到你的健康档案)里）。
  这条断言是为了让「谁顺手改了它」立刻现形，而不是等到演示当天

其中一组是**菜名匹配**，头两条不需要维护任何名单（遍历整张别名表，新加一条就自动被覆盖）：

- 别名表每个 value 都指向真实存在的 foodId —— 写错一个字母，今天的行为是
  **静默退回按名字匹配**，那条别名悄无声息地失效，不报错
- 别名表每个 key 自己走一遍完整匹配，必须落到它声明的那个 id（挡住「被前面某一层
  抢先命中成别的东西」—— 那样这张表在骗人）
- **「X汤」必须落到汤羹那一类**：两条已经给了别名的汤要落对，没有别名的汤
  （「山药排骨汤」）要**老老实实落空**，而不是被 `contains` 随手塞给某样蔬菜
- **golden 表 52 条**：真实菜名逐条钉死该落到哪个 foodId。上面那些是**结构**上的
  检查，这张是**行为**上的 —— 五个匹配层之间有顺序耦合，单看某一层的断言察觉不到
  串味。故意落空的 4 条写成 `null`，每条都是判断而不是遗漏（理由写在那张表上面）
- 故意落空的菜必须真的进 `unmatched` —— 否则结果页不会显示「按 0 计」那行警告，
  而热量会静静地少一块

同一份脚本里还有一组**分量三档**（[确认分量那一步](#确认分量那一步)的纯逻辑）：

- **数据守卫**：库里每个食物点「常规」都等于它自己的 `defaultGrams`。今天所有
  `defaultGrams` 都是 5 的倍数，这条恒成立；但它挡的是「谁加了一个
  `defaultGrams: 128`，取整把它悄悄变成 130」——**整个设计锚在「常规 = 库里的常见
  分量」上**，没有这条断言这种事不会有人发现
- 每个食物三档单调递增，且「多量」不超过 1000g（和 `clampGrams` 的上界对齐）
- 边界：炒花生 30g → 少量 20g（**不等于**常规，因为 30 × 0.6 取整到 5 才回来）；
  珍珠奶茶 500g → 多量 750g
- **「常规」是幂等的** —— 同一个食物换个初始克数连算两次结果相同（防「常规变成
  随机数」回归）
- **合并过的菜不被砍回去**：`米饭` + `白米饭` 归并成 300g 之后，点「常规」仍然是
  300g，点「多量」是 450g（这条专门防「静默砍回 150g」）
- **哨兵项不抛错**：拿真实的 `matchDishes` 产出（含 `unmatched:` 项）走完整映射，
  断言它原样返回 —— 上面那个 `FOOD_BY_ID.get(id)!` 的写法会在这里当场现形
- `countableItems` 过滤掉哨兵项、保留可算的项

**`npm run verify:agent`** —— 服务端转发自检。对着一个**本地假 Dify** 跑
`api/_lib/agent.ts`，不起真网络：

- `Authorization` 头确实被补上了
- SSE 是原样透传的（假上游分三次写，中间隔开）
- 上游 500 映射成 502 且带上机器可读的 `code`
- 空 query / 超长 query / GET 各自返回正确状态码
- 限流窗口内放行 12 次、第 13 次返回 429，且不误伤其他 IP
- 报错信息里不含 Key

**`npm run verify:reply`** —— 解析自检。夹具取自真实探测结果，覆盖四种 `mode`
和拦截分支，重点在**模型不守规矩时会不会崩**：

- 剥掉 ` ``` ` 围栏、挖出被客套话包住的 JSON
- 纯文本 / 空串 / 截断的 JSON / `{}` / 有 `blocked` 但没给理由 —— 一律返回 `null` 走降级
- `risk.level` 给了预期外的值 → 归到 `unknown`，不冒充结论
- `dishes` 里混进 `null` 和字符串 → 过滤掉，不崩
- `suitable` 字段缺失 → 视为适宜，不无端给用户标红
- 「每日 25-30 克」里的数字不被误当成编号切开

同一份脚本还接着跑了**客户端识别链路**（把 `/api/recognize` 换成一段写死的 SSE，
测的是客户端那一半）：

- 模型答「未知菜品 (图片无法识别)」时，**不把它当成一道菜**，也**不降级成本地演示数据**
  （模型明明看过那张图）
- 真菜里混了个占位名时，保留认得出的、丢掉占位名
- 正常菜名照旧匹配食物库
- **模型自己挑的 foodId 能穿过整条链路**（喂的是写死的 SSE，测的是真实三层：
  解析 → 转交 → 匹配）。这一节是后补的，起因是一个教训：这个字段原来在解析和
  转交那两层**各丢掉一次**，于是「在 Dify 提示词里加上食物库目录」这件事**完全
  没有效果，而且不报错**。而 `verify-loop` 里那两条 foodId 断言一直是绿的 ——
  因为它们直接调 `matchDishes`，没走这条路。**测试跑在错误的层上，比没有测试更糟**
- 编造的 foodId 被拒、退回按名字匹配；克数给 `"150g"` 这种字符串也能解析；
  解析不出的克数退回食物库默认值而**不是** 0

**`npm run verify:render`** —— 渲染冒烟测试。用 `react-dom/server` 把八个页面各渲染一遍
（七个走路由表；分析页因为它渲染什么完全取决于任务状态，单独测三种状态）：

- 没有组件在渲染期抛异常
- 每个页面确实渲染出了预期内容，不是一个空壳
- 直接刷新到结果页时给出的是**空状态**，不是白屏
- 渲染产物里不含真实姓名与未脱敏手机号

其中「确认分量」那一屏查得比其他页细，因为它的正确性靠的是**几个互相矛盾的约束同时
成立**（详见[确认分量那一步](#确认分量那一步)）：

- 每道菜都列出来、三档都在、**默认选中「常规」**、`role="radio"` 与
  `aria-checked` 的数量对得上（2 道菜 = 6 个选项 = 2 个组、2 个选中）
- 未收录的菜**出现了但没有控件**，标着「按 0 计」（用户拍了 3 道菜只看见 2 行，会
  以为 App 漏了）
- 降级路径：有「演示数据」横幅、**没有 `<img>`** —— 把真照片摆在编出来的菜旁边，
  等于暗示两者有因果关系
- `pending === null`（刷新、直接打开）给的是空状态和两条出路，不是白屏
- **接线检查**：渲染 harness 绕过了路由表，所以它直接读 `src/App.tsx` 与
  `AnalyzingScreen.tsx` 的源码，断言 `/portion` 这条路由在、且两跳都在往它跳。
  `App.tsx` 自己持有 `<BrowserRouter>`，在 Node 里渲染不了，只能这么验

还有一条**从确认分量到结果页的端到端断言**，用真的 `portionItems` 改完 `pending`
再渲染结果页：常规 → 150g / 174 kcal，少量 → 90g / 104 kcal，多量 → 225g / 261 kcal。
这条是这一步唯一能证明「用户的选择真的改变了结论」的东西。

结果页这边的反向断言同样重要：**「估算」两个字不再出现**（那个数字是常量，不是推断
结果），而且头部只在 `portionConfirmed` 为真时才说「分量由你选择」—— 全未收录和
没识别出菜这两条路会**跳过**这一步却仍渲染同一张卡，写在那就是在说一件没发生过的事。
另外那条「不把它当成一道菜渲染」的老断言换成了锚定边界的正则：`'150g'` 里就含
`'0g'`，朴素的 `!includes('0g')` 是自欺欺人。

日记页的幽灵警告也在这里验**接线**（逻辑在 `verify-loop`）：正常记录下**不出现**，
塞一条库外记录后出现、点名是哪道菜、并说明数字的后果，删掉那条记录后消失。
最后一条比的是**卡片数量**（`border-warn-line` 出现几次）而不是某句固定文案 ——
`幽灵卡是追加的，没有顶掉健康警示` 这件事只有比数量才验得动，写成
`includes('餐次记录')` 那种断言永远为真，是绿着的空壳。

再单独渲染一遍 `AgentReplyCard` 的四种形态。这个 agent 把 JSON 当回答文本吐出来，
所以最容易出的故障是「卡片渲染成空壳」和「没解析成功、把原始 JSON 糊到屏幕上」：

- 四种形态各自渲染出了菜名 / 建议 / 过敏原，不是空壳
- **渲染产物里不含 `"blocked"` 或 `\"`** —— 原始 JSON 没有漏到界面上
- Markdown 的 `**加粗**` 转成了 `<strong>`，没有露出星号

档案那几屏（建档引导 / 切换档案 / 编辑后的配额来处）也在同一份脚本里，它们盯的都是
**「渲染得出来」而不是「渲染得对」**——但有一条例外，那是最要紧的一条：

- **空档案渲染首页不出现 `NaN`** —— 引导建档完成时日记是空的，而 `derive.ts` 的除法
  没有零守卫。所以空档案的配额**不是零**，是从一个中性体征算出来的真实值
  （有一条断言盯着 `quotaFor(空档案)` 每一项都 > 0）。0 配额会让首页那行**无条件渲染**
  的百分比变成 `NaN%`，钠与蛋白质建议变成结构性不可达，危险色永远不出现
- 健康分在记录不足两餐时带一句「仅供参考」——`provisional` 这个字段以前**一个渲染点
  都没有**，是纯死代码，那条文案是补上的
- 每屏都能一键跳「先用演示档案看看」；`onboarded === false` 时整张路由表换成 `/welcome`
  （`App.tsx` 在 Node 里渲染不了，这两条是读源码断言的，见上面的接线检查）
- 「全部记录」的数字是**两份档案之和**；「清空记录」「恢复演示数据」点名的是当前档案
- 勾上慢性病之后，档案页出现「高血压 → 钠 1500mg」这一行来处；手改挡住条件调整时
  写成「未采用」并给出重新考虑的入口
- 对话页在 Node 里恰好就是「浏览器不支持语音」那条分支，所以那条断言同时证明了
  **按钮照常渲染**和**没有 speech API 时组件不抛**。说明面板是 `open` 为 prop 的
  独立组件，可以直接渲染开，断言它点了 Chrome 和 Safari 的名
  （`renderToStaticMarkup` 不跑 effect，所以依赖 `listening` 的界面在这里够不到 ——
  不写依赖它的断言，那正是下面这条「绿着的空壳」要防的东西）

**有一条断言找的是 `NaN`**：空档案 + 空日记渲染出来的 HTML 里不许出现这三个字母。
它比逐项检查便宜，而且覆盖了所有没被想明白的除法。

它不是视觉回归 —— 排版还得自己在浏览器里看。它挡的是"某个页面白屏了，
但要手动点进去才发现"这一类问题。

**`npm run verify:image` / `npm run verify:quota`** —— 图片与存储：

- `fitWithin` 的纯逻辑：长边约束、竖图、正方形、超小图不放大
- 缩略图写满配额时**不静默失败**，且去掉缩略图重试后**营养数据一条不少**（见
  [拍餐盘的真实链路](#拍餐盘的真实链路)）
- 多档案之后缩略图散在 `state.meals` 和 `state.profiles[i].meals` 两处，
  **降级重试要把两边都剥到** —— 只剥当前档案的话，那张碍事的照片在**别的档案**里，
  用户看到的是「存储空间不足，这一餐没能保存下来」，怎么看都跟眼前这一餐没关系
- 读盘的形状守卫：一份截断的载荷、或一个当前档案同时出现在 `profiles` 里的
  半写状态（`switchProfile` 写成「先写后查」会留下的那个），都要被丢掉而不是
  在渲染期抛成白屏

**`npm run verify:speech`** —— 语音输入的纯逻辑。

⚠️ **先说清这个脚本不能证明什么**：真的说话能不能转写、权限被拒之后什么样、
播过音频之后还能不能启动 —— 这些在 Node 里一条都验不了，只能人工在三端走一遍
（见[已知限制](#已知限制)）。一个跑得通的自检最危险的地方，就是让人以为功能被验证过了。

它验的是这个功能里**唯一会静默出错**的那部分 —— 错了不崩，只是让人用着别扭：

- `slotFor` 三态全覆盖，其中两条是刻意的：**正在听 + 输入框有字 → 仍然是「停止」**
  （`interimResults` 会把中间结果写进输入框，先判文字的话识别到一半按钮就跳成「发送」，
  用户根本按不到停止）；**回复中 + 输入框为空 → 麦克风**（食衡正一个字一个字往外吐的
  时候，用户完全应该能开始说下一个问题 —— 那是麦克风，不是正在被占用的网络连接）
- **转写文本是替换不是追加**：喂三次事件，断言最后**恰好**是那句话而不是
  `今天今天盐今天盐吃…`。旁边还有一条反面断言（「按追加写会得到另一个字符串」），
  证明上面那条不是恒真的空壳
- `errorLine('aborted', true) === null` 而 `aborted + false` 有话说 ——
  `plate.ts` 里那条「用户按的停止不是故障」的区分，在这里变成可检的
- 八个错误码全都有话（`SpeechRecognitionErrorCode` 是 8 个成员，不是 5 个），
  没写文案的走兜底，不吐 `undefined` 到界面上
- **看门狗用假时钟驱动**：超时触发一次、不重入、取消之后即使回调仍然到达也不触发。
  不这么做的话，这个函数就是一句「一个从没被观察到触发过的说法」
- 最后两条是**结构性**的：`speech.ts` 和 `useSpeech.ts` **必须能在 Node 里被导入**。
  任何模块顶层的 `window.SpeechRecognition` 都会让 `verify-render` 在导入期抛
  `ReferenceError`，而那句 `ssrLoadModule` 写在 `try` 之外 —— 脚本当场死在未捕获的
  顶层 await 上，**后面每一节都不再运行**。这条断言盯的是那个失败模式本身

**`npm run probe:vision`** —— 真实视觉链路探测。要另开一个终端跑着 `npm run dev`，
它会发一张真图给真 Dify，回答「模型到底看见图了没有」。
**这是唯一能回答这个问题的东西** —— 光看返回内容分辨不出来，因为没开 Vision 时模型
照样会编出一份格式正确的菜品清单。跑法见脚本头部的注释。

**`npm run probe:dishes`** —— 菜名匹配探测。不需要 Key、不需要网络，纯本地跑：
把 98 个真实菜名（家常菜、外卖菜名、食堂菜、模型爱加的分量前缀，外加一批复合菜名）
喂进匹配链路，按层统计命中数、列出落空清单，并把 `contains` 那一层单独摊开逐个看。

它回答的是**「库里缺哪些菜」** —— 这件事在界面上看不见，用户看到的只是一条警告框和
几行按 0 计。要扩充食物库或别名表，得先知道缺的是哪些，**不能靠回忆自己昨天吃了什么**。
这一轮就是它先说话：98 个里落空 21 个（21%），补完之后落空 4 个（4%）。

它同时盯一类更隐蔽的问题：`contains` 是唯一会**跨过菜名本身**去命中的一层，也是唯一
会产出**静默错配**的一层。它揪出过两个 —— `番茄鸡蛋汤 → 番茄(生)`、`玉米排骨汤 →
玉米(煮)`，两道汤各被算成一份生蔬菜，而界面上看不出任何异常。所以脚本把多出 3 个字
以上的命中额外标出来：多 1 个字通常是修饰（糙**米**饭、卤**牛**肉），多 3 个字往往
命中的是半道菜。

**这份清单不是测试，是排查工具** —— 它的输出需要人看，防回归的是 `verify-loop` 里
那张 golden 表。

**`npm run probe:ghost`** —— 幽灵条目变异测试。不需要 Key、不需要网络：

它真的从 `FOOD_BY_ID` 里**删掉一条今天的记录正在用的食物**，然后打出删除前后的热量、
钠、健康分，以及探测器有没有抓到。它回答的是**「记录里的 id 在库里没了，这件事
到底有多大代价、App 会不会告诉你」** —— 跑一次就看得见（实测 943 → 739 kcal、
健康分 96 → 92）。

为什么这件事要用真数据做变异，而不是像 `verify-loop` 那样用夹具：**夹具的形状可能
和真实数据对不上，那时测试会绿着骗人**。这个仓库已经栽过一次（两条 foodId 断言一直
是绿的，但它们直接调 `matchDishes`，而客户端在那之前就把字段丢了）。所以这一条必须
在真实记录上变异，顺带也就证明了探测器不是只在夹具上会响。

它必须独立成一个脚本：变异是**进程内**的，塞进 `verify:all` 会污染后面所有依赖食物库
的断言（而且删掉再插回去会把 `Map` 的迭代顺序改掉）。

## 已知限制

写清楚这些，是因为**把假数据说成真数据，比用假数据本身更糟**。

**食物成分表是近似值。** `src/data/foods.ts` 里约 60 种食物的数值是按常见认知整理的，
不是逐条核对《中国食物成分表》来的。文件头和「我的」页都标注了这一点。
精度不足以支撑任何真实的营养、医疗或健康决策。
要换成权威数据集的话，接口不用改 —— 数据结构统一按「每 100g」设计。

**拍照识别走的是真模型，但认得多准取决于你的 Dify 应用。** 图片真的会被送去多模态
模型（链路见[拍餐盘的真实链路](#拍餐盘的真实链路)）。但有 Key 才有模型 ——
打开演示链接的人没有，所以那时退回本地随机组菜，并**在结果页最上面明说这是演示数据**。

**本地建议引擎挡不住复合菜品的过敏原。** `advice.ts` 是按菜名里含不含「花生」这种
子串判的，而「宫保鸡丁」这四个字里没有「花生」。所以拍餐盘这条路上，真正在兜过敏的
是 **Dify 工作流的节点 7**，不是本地引擎。**没配 Key 的时候这条防线是不存在的** ——
那会儿界面上的所有营养数字都是演示数据，请按演示数据看待它们。

**日记里只存缩略图，不存原图。** `MealEntry.thumb` 是一张 200px 的 data URL，
用来在列表里认出「这是哪一餐」。原图只在内存里活一次，用于确认识别对不对，
从不落盘、也不上传到别处。

**分量不会自动估算，是让用户自己选的。** 模型只给菜名，所以出结果前有一屏让用户
按少/常规/多确认一遍（[见上](#确认分量那一步)），细调还是到结果页点「调整分量或增删菜品」。
想真让模型估重得改 Dify 提示词 —— `matchDishes` 本来就接受可选的 `foodId` 和 `grams`，
提示词里加上这两个字段就生效，App 一行都不用改（**有就用，没有就用默认值**；
「确认分量」的基准也特意这么取，正是为了那一天不用回来改）。

**食物库只有 58 项，复合菜名大概率匹配不上。** 别名表补过一轮之后（见下），
一份家常菜大约还有 **4%** 会落空，「土豆炖牛肉」「豆腐菌菇汤」「煎饼果子」这类
名字库里确实没有对应项。匹配不上的**不会被静默丢掉也不按 0 悄悄混过去** ——
结果页会显式列出「这 N 项不在食物库里，暂时按 0 计」，并引导去修正。
不这么做的话，用户会拿到一个悄悄偏低的热量和一个悄悄偏高的健康分，而界面上看不出异常。
想再少一些的话有两条路：[提示词里加食物库目录](#让模型从食物库目录里挑以及知识库该用在哪)
（让模型在封闭集合里挑 foodId），或者扩库。**两条都到不了 0，也不应该到 0** ——
目标不是「永远不落空」，是「每一处不确定都被标出来」。

**食物库改版会制造「幽灵条目」，这是另一条、而且更隐蔽的 0。** 上面那条说的是
「识别时库里没有」；这一条说的是**记录里那个 id 后来从库里消失了** —— 改个 id、
删掉一条重复的菜，旧记录就指向了一个不存在的东西。它同样按 0 计，但和上面那条
有一个致命区别：**它是静默的**。日记、周趋势、首页健康分会一起偏低，而界面上
看不出任何异常。代价是量出来的（`npm run probe:ghost` 真的删掉一条今天在用的食物）：

```
  删除前：943 kcal · 钠 1183mg · 健康分 96
  删除后：739 kcal · 钠 1093mg · 健康分 92      ← 数字全变了，而修之前屏幕上一句话都没有
```

现在日记页会挂一张卡点名是哪几道菜 —— 靠的是 `MealItem.name`（`types.ts` 里那句
「冗余存一份名字：食物库换版本后旧记录仍能显示」说的正是这个场景，名字早就备份了，
只是以前没人拿它来说话）。

**为什么不做软删除**（把下架的食物留在库里不删）。那样数字能原样保住，但会换出一个
**新的静默**：退休的条目还在参与计算，而没有任何地方说明它已经不推荐了。这和上面
别名表那条取舍是同一个立场 —— 宁可把不确定说出来，也不要一个悄悄正确的数字。
报出来之后修法由人定：把 id 改回现有的那条，或者把缺的那条补回库里。

**这条路径由 `npm run verify` 的一组断言盯着**，其中最关键的一条不是「能抓到幽灵」，
而是**「哨兵不算幽灵」** —— `unmatched:` 开头的那种（拍了库外的菜）同样不在食物库里，
但含义完全相反。不排除它的话，用户每拍一道库外的菜日记页就多一条假警报，而假警报
的代价是这个真警报再也没人看（同一个道理见[上面 probe:vision 那个恒亮的红灯](#接入-dify-agent)）。

**别名表是「模型说 A、库里叫 B」的唯一显式记录处**，`matchDishes` 里那张表
（`src/lib/dishMatch.ts` 的 `DISH_ALIASES`）收的是**同一道菜的相近版本**
（糖醋排骨 → 红烧排骨、罗宋汤 → 番茄牛腩汤）。**「某个成分像」的一律不收** ——
「土豆炖牛肉」库里只有卤牛肉可用，但土豆在那道菜里占一大半重量，映射过去等于把
一份带主食的菜算成一小碟瘦肉：那是个看起来合理的错数字，比一条「未收录、按 0 计」
的警告糟得多。收进来的每一条都是近似而非精确（糖醋汁里的糖、炒饭里的油都没算），
偏差方向统一**偏低** —— 宁可低估，不要编一个高的。

怎么知道缺哪些菜？**不能靠回忆自己昨天吃了什么**，跑 `npm run probe:dishes`：
它把 98 个真实菜名喂进匹配链路，按层统计命中、列出落空清单、并把 `contains`
那一层单独摊开（那层唯一会产出**静默错配**）。这一轮就是它先揪出来的：

| 探针发现 | 问题 | 处理 |
|---|---|---|
| 98 个菜名落空 21 个（21%） | 家常菜名大面积没覆盖 | 别名表补 22 条 + 库里补 2 条 → 落空降到 4 个（4%） |
| `番茄鸡蛋汤 → 番茄(生)` | **一道汤被算成一份生番茄** | 补别名；再加一条结构规则兜住没预料到的汤名 |
| `玉米排骨汤 → 玉米(煮)` | 一道汤被算成一根玉米 | 同上 |

第二条不是打补丁，是**改了 `findContains` 的规则**：名字以「汤」结尾的必须落到
`汤羹` 那一类，否则跳过这个候选。理由是这类错配和「组合名被当成一道菜」是同一个
失效模式 —— **落空会在界面上被标出来，错配不会**。库里也确实有 `汤羹` 这个分类，
不用另造概念。

**模型报「一餐」而不是「一道菜」时会被拆开。** 实测工作流有时会落到推荐分支，
`dishes` 回来的是「燕麦粥 + 煮鸡蛋 + 牛奶」这种组合名。`matchDishes` 会按 `+` / `＋` / `、`
拆成单道菜再各自匹配 —— **不拆的话更糟**：双向包含匹配会把整串名字当成一道菜，
取「包含得更长」的那个，于是「清蒸鱼 + 白灼西兰花 + 米饭」变成一条西兰花，
鱼和米饭静默消失。那种错不会进 `unmatched`，界面上完全看不出来。
（模型若显式给了 `grams` 或 `foodId` 则**不拆** —— 那是它明确指出的一份东西，
拆开会让克数翻倍。）

**没有做 `getUserMedia` 自绘取景器，所以「拍照」在 iOS 和桌面上不真的开相机。**
用的是 `<input type="file" capture="environment">`：只有 **Android Chrome** 会直接
打开相机 App；**iOS Safari 会弹它自己的单子**（拍照 / 照片图库 / 浏览文件），
`capture` 不能强制进相机（WebKit Bug 236981）；**桌面浏览器完全忽略它**，
退化成文件选择器。所以「拍照」和「从相册选择」这两个入口的差别只在 Android 上成立。

要三端一致地开相机，就得用 `getUserMedia` + 自绘取景器：要 HTTPS（`localhost` 算安全
上下文，局域网 `http://192.168.x.x` 不算）、要处理权限申请与拒绝后无法再次申请的情况、
要自己画取景器和快门。这个演示的收益不值那个复杂度 —— 而且它并不改变"图片能不能
送到模型"这件事，只改变"用户从哪儿拿到图片"。另外**没有浏览器层的相机权限弹窗**
也正因为如此：这条路上浏览器把拍照交给了系统相机（或 iOS 的单子），
权限归系统管，页面本身从不申请摄像头。

> ⚠️ **这句话只对摄像头成立。麦克风是另一回事** —— 对话页的语音输入走的是
> 浏览器的 `SpeechRecognition`，点麦克风时**会**弹出浏览器层的麦克风权限请求，
> 而且**被拒绝之后 iOS Safari 不允许页面再次申请**，只能到「设置 → Safari → 麦克风」
> 里改回来（和上面 `capture` 那个坑是同一个浏览器、同一类限制）。

**膳食纤维和饮水不计入健康分。** 档案里有目标值，但食物库没有纤维数据，
饮水也没有录入入口。它们在界面上只作为展示目标存在。

**盐和钠没有混用。** 设计稿这里是不一致的：档案页写「钠 5g」，结果页却拿「500mg」
当上限，差了 10 倍 —— 实际是把**食盐**和**钠**混为一谈了
（食盐 ≤ 5g/日 ≈ 钠 1965mg）。代码里统一用**钠 2000mg/日**，与食物库的 mg 口径一致。

**添加糖单独追踪。** 水果的果糖、牛奶的乳糖**不**计入添加糖，
只有加工时额外加入的才算。这个区分很重要，否则「控糖」会变成「别吃水果」。

**多档案了，但切换会换掉整套日记。** 每个档案有自己的日记和每日目标（这是刻意的：
「膳食分析基于当前档案生成」的副标题写着「当前」，就必然有「其他」）。代价是
**切换档案之后首页、日记、健康分全都换成另一份记录** —— 不是同一个日记换个名字。
面板里每一行都写着它有多少条记录，就是为了让这件事在点之前看得见。
「清空记录」和「恢复演示数据」只作用于**当前**档案，按钮上点了名。

**语音输入在三端表现不一样，而且有一半我验不了。**

| | 情况 |
|---|---|
| Chrome / Edge | 能转写。**音频由 Chrome 送到 Google 的识别服务**，不走本项目的服务端 |
| Safari（含 iOS） | 能转写，走 Apple。iOS 上被拒之后**页面内无法再次申请** |
| Firefox | **默认没有这个接口**。按钮照常渲染，点开是说明面板 |
| 加密上下文 | 必须 https（`localhost` 例外）。http 的局域网地址上麦克风根本不会启动 |

**下面这些我只写了代码，没有在现场看到过，所以标成未验证，而不是当成事实：**

- **看门狗**（8 秒没有任何事件就认定挂住、主动收摊并说明原因）。它挡的是
  WebKit bug 317741 / 321436 —— **播过音频之后 `start()` 会挂住且一个事件都不发**，
  界面永远停在「正在听」，用户只能刷新。这个 bug 的现场我没复现过，
  超时的行为只有 `verify:speech` 里用假时钟驱动的那几条断言，
  **在真机上从没见它触发过**
- **`continuous: false` 在各引擎的实际行为**（我以为都是「第一次停顿就结束」，
  只按这个假设写了）
- 权限被拒之后那条提示在各浏览器上的实际文案（`not-allowed` 那一支）

**输入框里有字时，麦克风够不着。** 麦克风/发送/停止共用一个槽位（输入栏只有 4 格，
再塞一格会把输入框挤到 ~114pt）。所以想口述得先把输入框清空。两个槽位装三个状态
本来就丢一种情况，而 114pt 的输入框不是选项。

**语音转写的结果不会自动发送**，只落进输入框。中文菜名的识别错误率不低
（「清蒸鱼」/「青蒸鱼」），自动发出去等于把这层错误直接送给模型。

**`SCHEMA_VERSION` 升到 3 了，所以打开过旧版本的人本地记录会重置一次。**
这个仓库对演示数据的一贯政策是「没有迁移价值，丢弃即可」（v1→v2 也是这么处理的），
代价就是这一次重置 —— 换来的是一份能装下多档案和三个新字段的载荷。

**Agent 读得到健康档案，但依赖上游一处修复。** App 每次提问都会把档案和
今日摄入塞进 query 的 JSON 发给 agent，节点 2 解析后喂给拦截逻辑和提示词。
**这条链路是否生效，取决于那个 Dify 应用有没有修过节点 7 的全量扫描 bug** ——
没修的应用会把「避免花生」这种正确建议当成命中并拦截，
而且不确定（同一句话两次跑可能一次拦一次不拦）。

`npm run probe` 的第一对对照实验就是用来回答「当前这个应用能不能用」的：
两个对照都过，再打开 `SEND_PROFILE_TO_AGENT`。完整改法和验证方式见
[让 agent 读到你的健康档案](#让-agent-读到你的健康档案)。

**同一句话，两次的回答形态可能不同。** `mode` 由模型自己选，不是调用方指定的。
实测同一个「三天控盐食谱」，一次返回 6 道菜的菜单、一次返回 9 道，
菜式也完全不同。渲染层五种 `mode`（`fridge` / `plate` / `dish` / `menu` /
`ingredient`）都兜住了，但如果你在 Dify 里改了 prompt、加了新的 `mode`，
前端会认不出来 —— 那种情况不会白屏（退回纯文本），但会显示成一坨 JSON。
改完之后跑 `npm run probe` 确认一下。

**`fridge` 模式的食材清单前端没渲染。** 提示词里 `fridge` 是「识别食材 →
`ingredients`」+ 推荐 2–4 道菜，但回复卡片只读 `dishes`，那份食材清单会丢。
不影响演示（不崩、不白屏）但「冰箱里有啥」这个场景少了一半信息。

**知识库：本机能验的都验了，检索本身没验过。**

文档生成、覆盖检查、反向核对（从写出去的文件里读回钠值再和 `quotaFor()` 比）
都在本机跑得通，也都有断言。但**「导进 Dify 之后检索真的会命中吗」这件事，
我没有验过** —— 它需要 Dify 的界面和日志，而那在浏览器里，不在这个仓库里。

所以到目前为止，知识库的状态是：**内容就绪、链路未通**。要变成「通了」还需要两步：

1. 把 `dify/knowledge/` 整个导进 Dify（15 份），按[路径 B](#路径-b知识库用在对话页)那三步配分段/索引/检索
2. 把检索节点的查询文本从 `用户输入.sys.query` 改成上游「代码执行」节点的 `text`

之后跑 `npm run probe:kb`。但注意它的判据是**单向**的：答对不算证据（慢性病
饮食建议是公开常识，没接知识库的模型也答得出来），只有答错才是证据。真正的
决定性证据在 Dify 的运行日志里那个检索节点的命中条数 —— 这个脚本看不到。

**慢性肾病那条是个已知的简化。** 官方指南（《成人慢性肾脏病食养指南（2024年版）》）
按分期给蛋白质：1～2 期 0.8 g/kg、3～5 期 0.6 g/kg，**而且都以「理想体重」
（身高 − 105）计**。App 里没有「分期」这个字段，取的是 1～2 期那个较宽松的值、
并且用实际体重算 —— 也就是说，一个 3 期以上的用户会拿到偏宽松的数字。

这一条没有偷偷改算法，而是**写进了依据里**（档案页和 `01` 号文档都能看到），
因为「App 该按哪个期给」本身就是个产品决定，不该由我替他定。要真正修好，
得在档案里加「慢性肾病分期」这个字段 —— 而这会牵动引导、编辑面板、
`quotaFor()` 的 `DELTAS` 表和 KB 文档四处的口径。

## 隐私

这个仓库要推到 GitHub，所以敏感信息一律隔离在 `private/`（已被 `.gitignore` 排除）：

- Figma Token、Dify App Key
- Figma 原始导出（`private/design/`）—— 里面含有设计稿上的全部文字，包括账号昵称

`knowledge-base/`（知识库的**原始素材**：官方指南 PDF、提取出的 txt、转录后的 md）也
在 `.gitignore` 里。两条理由，任何一条单独成立就够：**体积**（光 PDF 就 120MB 以上，
GitHub 对单文件还有 100MB 的硬上限），以及**版权** —— 官方指南是可以引用的公开文件，
但那本 `让家人吃出健康.pdf` 不是。这个仓库是给人点开看的，不该顺带分发别人的书。

生成物 `dify/knowledge/` 反过来**进**仓库：它是喂给 Dify 的成品，体积小，
而且读的人需要它才看得懂路径 B 最后落地成了什么。

仓库里**没有**任何真实个人信息：`src/data/mock.ts` 的姓名、手机号、邮箱全部是占位符
（`示例用户` / `138****0000` / `user@example.com`，`example.com` 是 RFC 保留域名）。
设计稿里原本硬编码的真实姓名和手机号没有被复制过来 ——
个人信息一旦进仓库就会留在提交历史里，事后删除也清不掉。

**什么东西会离开这台设备**（这是本节唯一列这张清单的地方，缺一条就等于没说）：

| 什么东西 | 去哪儿 | 什么时候 |
|---|---|---|
| 档案 + 当天摄入的数字（**不含姓名**） | 你的 Dify 应用 | 每次在对话页提问。档案页填的特殊时期/慢性病/偏好都在里面 |
| 你选中或拍的那张照片 | 你的 Dify 应用 | 每次拍餐盘识别 |
| **你对着麦克风说的话（音频本身）** | **Chrome → Google / Safari → Apple** | 每次点麦克风。**不经过本项目的服务端、不经过 `/api/*`、不经过那个限流** |
| 知识库那 15 份文档 | 你的 Dify 应用 | **一次性**，导入 Dify 的时候。里面没有任何个人信息 —— 是官方指南原文加本 App 自己的配额说明 |

健康记录只存在浏览器本地的 `localStorage`，不上传到任何服务器 ——
**除了上面那几条**（拍照和语音是其中两条）。

关于语音那一条要说透：`SpeechRecognition` 是**浏览器自己**把音频送去识别服务的，
走的是浏览器厂商的通道，开关在用户和浏览器手里 —— 本项目的代码**没有**、
也拿不到那条链路的任何控制点。能做的只是把它写在这里、并在点麦克风时让浏览器
按规矩弹出权限请求。这也是为什么它单独占一行，而不是并进「问问题时发给 Dify」那条里：
那条是我们发的、我们知道发了什么；这条不是。

## 设计来源

界面按 Figma 文档「食衡 MealBalance」的「③ 界面原型」还原，共七个界面。
`design/tokens.json` 是从设计稿提取的变量（26 个颜色 + 字号 + 圆角），
由 `scripts/fetch-figma.mjs` 生成。

**三屏是原型里没有、为了跑通闭环而新增的**：`MealSheet`（记录一餐）、
`QuotaSheet`（调整每日目标）和 `PortionScreen`（确认分量）。
原型是视觉稿，画的是「信息怎么呈现」，没有画「数据从哪来」—— 但没有录入界面，
日记永远是空的、健康分永远不变，整个 App 就还是一套会动的设计稿。
三屏都沿用了原型的设计系统（顶部圆角 24、`#FAFAFC` 底、抓手条、底部安全区），
保持 iOS 手感一致。

### 有意偏离设计稿的文案

设计稿里三处文案被**故意改掉**了，不是手滑 —— 记在这里，免得看起来像实现走样。
稿子（`private/design/figma-raw.json`）里是：

| 稿子里 | 现在 | 位置 | 为什么改 |
|---|---|---|---|
| 「估算 150g」「估算 200g」 | 「150g」 | `:61610` / `:62349` / `:63088` | 那个数字是 `data/foods.ts` 里的常量，不是从照片推出来的。用「估算」这个词，等于把一个常量说成推断结果 —— 这个仓库最在意的事就是不许这样（见[已知限制](#已知限制)） |
| 「识别菜品**与估算分量**」（分析中的第一步） | 「识别菜品」 | `:73592` | 改完之后 App 不再估算分量（由用户在下一步选），这句话会变成**新的一句假话** |
| 「识别菜品 · **估算分量** · 计算营养 · 风险分级」（首页 CTA） | 「识别菜品 · 确认分量 · 计算营养 · 风险分级」 | `:32796` | 同一句话的第二份拷贝。两处必须一起改，否则首页还在宣称老模型 |

界面上只剩一处「估算」：全未收录那条路写的「没法估算营养」—— 那句是**诚实的**，
它说的正是「这件事我做不到」。`verify:render` 盯的是「估算 + 数字 + g」这个组合，
不是「估算」这个词，就是为了不把那一句连坐掉。

新增的 `PortionScreen` 不是「偏离」，是**补一屏**：设计稿假设照片能估出克数，
这件事做不到，所以把这个问题交还给唯一知道答案的人 —— 完整理由见
[确认分量那一步](#确认分量那一步)。
